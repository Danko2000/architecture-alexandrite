## 1. Мотивация внедрения мониторинга

Система компании обрабатывает растущее количество заказов, а ключевые проблемы (задержки, зависания, потери сообщений, перегрузка MES) напрямую влияют на **сроки выполнения заказов**, **качество клиентского опыта** и **контракты с партнёрами**.

Без мониторинга:
-  Проблемы фиксируются постфактум по жалобам клиентов.  
-  Нет прозрачности производительности системы.  
-  Сложно оперативно реагировать на деградации.  
-  Масштабирование и улучшения инфраструктуры выполняются «вслепую».

С мониторингом:
-  Аварии выявляются **до** того, как они затронут клиентов.  
-  SLA и стабильность повышаются.  
-  У команды появляются метрики для планирования масштабирования и оптимизации.  
-  Становится возможным **автоматическое реагирование** на инциденты.  
-  Упрощается анализ инцидентов и постмортемы.

>  Мониторинг делает систему управляемой и предсказуемой при росте нагрузки.

---

## 2. Выбор подхода к мониторингу

В системе есть несколько компонент с разной природой нагрузки:

| Компонента | Тип нагрузки | Рекомендованный подход | Обоснование |
|------------|--------------|-------------------------|-------------|
| Веб-приложения (Shop API, CRM API, MES API) | Запросно-ориентированные сервисы | RED + Четыре золотых сигнала | RED — для RPS, ошибок и задержек; Золотые сигналы — для насыщенности |
| Очереди (RabbitMQ) | Поток сообщений | USE + RED | USE — для загрузки и насыщенности брокера; RED — для обработки сообщений |
| Базы данных | Ресурсы с чувствительностью к нагрузке | USE | Чёткое измерение утилизации, насыщенности и ошибок |
| S3-хранилище | Вспомогательный ресурс | USE (упрощённо) | Контроль размера и доступности |

## 3. Метрики по компонентам

### 3.1. Веб-приложения (Shop API, CRM API, MES API)  
 Подход: RED + Четыре золотых сигнала

| Метрика | Зачем | Ярлыки (labels) |
|---------|-------|-----------------|
| Number of requests (RPS) | Отслеживание трафика и пиковых нагрузок | service, endpoint, user_id |
| Response time (latency) | Контроль времени отклика, SLA | service, endpoint |
| Number of HTTP 200 | Базовый индикатор успешных ответов | service |
| Number of HTTP 500 | Ошибки серверной стороны | service, endpoint |
| CPU % | Утилизация ресурса, рост нагрузки | service |
| Memory Utilisation | Признак утечек памяти и перегрузки | service |
| Number of simultanious sessions | Поведенческая нагрузка | service |
| Kb transferred (received/sent) | Оценка сетевой нагрузки | service |

**Пороговые значения:**
- Задержка > SLA = алерт.
- Насыщенность по CPU > 80% и/или memory > 75%.

---

### 3.2. Очереди (RabbitMQ)  
 Подход: USE + RED

| Метрика | Зачем | Ярлыки |
|---------|-------|--------|
| Number of messages in flight | Отслеживание текущей нагрузки | queue |
| Number of dead-letter-exchange letters | Ошибки и неуспешные обработки | queue |
| Requests rate (publish/consume) | Измерение активности | queue |
| Errors (DLQ growth) | Сигнал проблем с обработчиками | queue |
| Utilization (CPU/Memory брокера) | Загрузка RabbitMQ | node |
| Saturation (queue length) | Накопление необработанных сообщений | queue |

**Пороговые значения:**
- Saturation > 80% длины очереди = потенциальный перегруз.  
- DLQ > 0 = алерт.

---

### 3.3. Базы данных (Shop DB, MES DB)  
 Подход: USE

| Метрика | Зачем | Ярлыки |
|---------|-------|--------|
| CPU % | Загрузка инстанса | db_instance |
| Memory Utilisation | Использование памяти | db_instance |
| Number of connections | Проверка насыщенности пулов | db_instance |
| Size of db instance | Рост объёма, необходимость масштабирования | db_instance |
| Errors (connection failures) | Надёжность соединений | db_instance |

**Пороговые значения:**
- CPU > 75% устойчиво в течение 5 мин — алерт.  
- Connection > 90% max pool size — алерт.

---

### 3.4. Хранилище (S3)  
 Подход: USE (упрощённый)

| Метрика | Зачем | Ярлыки |
|---------|-------|--------|
| Size of S3 storage | Планирование ёмкости и стоимости | bucket |
| Errors (access failures) | Проверка доступности | bucket |

**Порог:**  
- Size > 80% от плановой квоты — предупреждение.

## 4. План действий по внедрению мониторинга

1. **Создать инстанс time-series БД**  
   - Использовать Prometheus для хранения метрик.

2. **Развернуть визуализацию**  
   - Grafana с дашбордами по сервисам: API, RabbitMQ, БД, S3.

3. **Интеграция метрик с сервисами**  
   - Экспортеры для Java, C#, RabbitMQ 

4. **Настроить алертинг**  
   - платформы коммуникации, e-mail уведомления, автогенерация тикетов.

5. **Определить SLA и SLO по ключевым сервисам**  
   - Зафиксировать значения порогов для реакций.

6. **Автоматизация реакции**  
   - Autoscaling при превышении ресурсов.  
   - Автоматическая постановка задач при критических алертах.

7. **Регулярный аудит метрик**  
   - Добавление и уточнение метрик по мере роста системы.

## 5. Показатели насыщенности и реакция системы

Показатели насыщенности (Saturation) показывают, насколько ресурсы системы загружены ближе к пределу производительности.  
Выбор метрик и порогов позволяет:
- заранее выявлять деградацию;
- предотвращать очереди и отказы;
- реагировать автоматически, а не вручную.

### 5.1. Пороговые значения насыщенности

| Компонент | Метрика | Пороговое значение | Обоснование |
|-----------|---------|---------------------|-------------|
| Shop API | CPU Utilization | 80% | При нагрузке выше 80% растёт латентность и вероятность ошибок 5xx. |
| MES API | CPU Utilization | 80% | MES — ключевой сервис. Нужен запас для пиков. |
| CRM API | CPU Utilization | 75% | CRM менее критичен по SLA, но требует стабильности. |
| Все API | Memory Utilisation | 75% | При превышении — риск утечек, сбросов GC и деградации. |
| RabbitMQ | Queue Length | 80% от max queue | Сигнал, что обработчики не справляются с нагрузкой. |
| RabbitMQ | DLQ > 0 | Любое положительное значение | Ошибки доставки сообщений. |
| DB (Shop, MES) | Connections | 90% max pool | Опасность блокировок и таймаутов. |
| DB (Shop, MES) | CPU Utilization | 75% | После этой точки производительность падает. |
| S3 | Capacity | 80% от квоты | Возможен отказ при записи или рост стоимости. |

---

### 5.2. Действия при превышении порогов

| Компонент | Метрика | Реакция системы                                                                                                                                                       |
|-----------|---------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Shop API / MES API / CRM API | CPU > 80% | 1. Отправка уведомления в платформу для коммуникации . 2. Автоматическое добавление инстанса через авто-масштабирование. 3. Логирование события. |
| Shop API / MES API / CRM API | Memory > 75% | 1. Алерт. 2. Проверка логов на утечки. 3. Создание тикета для DevOps/разработчиков.                                                                                   |
| RabbitMQ | Queue Length > 80% | 1. Уведомление. 2. Добавление обработчиков (autoscaling workers). 3. Повышение приоритета задач на обработку.                                                         |
| RabbitMQ | DLQ > 0 | 1. Немедленное уведомление. 2. Создание тикета с логами сообщений. 3. Анализ источника ошибок.                                                                        |
| DB | Connections > 90% | 1. Уведомление. 2. Горизонтальное масштабирование (read replicas / пул). 3. Создание тикета.                                                                          |
| DB | CPU > 75% | 1. Уведомление. 2. Проверка долгих запросов. 3. Автомасштабирование или репликация.                                                                                   |
| S3 | Capacity > 80% | 1. Уведомление. 2. Плановое расширение хранилища. 3. При критическом превышении — тикет в поддержку провайдера.                                                       |

---

### 5.3. Уровни реакции и эскалации

| Уровень | Условие | Действие                                                                                    |
|---------|---------|---------------------------------------------------------------------------------------------|
| Warning | Порог достигнут впервые, 1–2 минуты | Отправка уведомления в платформы коммуникации, логирование                                  |
| Critical | Порог удерживается более 5 минут | Авто-масштабирование / алерт на on-call инженера                                            |
| Severe | Порог превышен критически (например, 95%) | Автоматическое создание тикета, вызов on-call, возможно автоотключение некритичных нагрузок |

---

### 5.4. Причины выбора таких порогов

- **80% по CPU и памяти** — после этого значения начинается резкая деградация производительности и нестабильное поведение сервисов.
- **90% по соединениям с БД** — позволяет оставить небольшой «аварийный запас».
- **DLQ > 0** — индикатор ошибок, которые в нормальном режиме не должны происходить.
- **80% ёмкости S3** — превентивная мера до начала отказов записи и резкого роста стоимости хранения.

---

### 5.5. Пример цепочки реакции

**Сценарий:** Нагрузка на MES API растёт, CPU достигает 85%.
1. Prometheus фиксирует превышение порога.
2. Grafana Alerting отправляет сообщение на платформу коммуникации.
3. Автоматически создаётся тикет в системе инцидентов.
4. Kubernetes (или autoscaler) добавляет новый инстанс MES API.
5. Через 2–5 минут нагрузка стабилизируется.
6. Инцидент закрывается автоматически или инженером после верификации.
