
## 1. Введение

Компания **«Александрит»** развивает экосистему для создания и продажи ювелирных изделий.  
Ключевая особенность — возможность загрузки и расчёта стоимости индивидуальных 3D-моделей украшений.

Текущая система состоит из трёх основных приложений:
- **Интернет-магазин** (B2C, Vue + Spring Boot)
- **CRM** (Vue + Spring Boot)
- **MES** (React + C#)

Интеграция между системами реализована через **RabbitMQ**.  
Хранение данных — **PostgreSQL**, файлы — **S3-хранилище**.  
Всё размещено в **Yandex Cloud**, по одному инстансу на приложение и одну БД на запись/чтение.

## 2. Текущее состояние архитектуры

Основные потоки данных:
1. Пользователь создаёт или загружает 3D-модель через **онлайн-магазин**.
2. Модель передаётся в **MES API**, который рассчитывает стоимость (до 30 мин для сложных моделей).
3. **CRM** получает результаты расчёта через **RabbitMQ**, управляет заказами и статусами.
4. **MES** предоставляет интерфейс операторам для производства и отслеживания заказов.
5. API внешних партнёров (B2B) направляют заказы напрямую через MES и RabbitMQ.

## 3. Идентифицированные проблемы

### 3.1. Производительность и масштабирование
- Все сервисы и базы работают в **одиночном инстансе** → нет горизонтального масштабирования, отсутствует HA.
- **MES API** сильно загружен при пиках из-за синхронных расчётов стоимости.
- Очередь **RabbitMQ** не мониторится и не масштабируется — при большом количестве сообщений возникают задержки и потери.
- Отсутствие **rate limiting** и **backpressure** для внешних API-партнёров → MES перегружается.

### 3.2. UX и производительность MES
- MES-дэшборд операторов загружает все заказы (даже с пагинацией) → перегружает БД, UI, сеть.
- Нет индексации по ключевым полям (дата, статус, оператор), что ухудшает отклик.
- Отсутствует кеширование "новых заказов" — каждый вход вызывает тяжёлые SQL-запросы.

### 3.3. Надёжность интеграций
- Межсистемная интеграция через RabbitMQ без DLQ (Dead Letter Queue) и без ретраев → при ошибке сообщение теряется.
- Нет **трассировки событий** между CRM–MES–Shop, невозможно отследить, где застрял заказ.
- При сбое MES API невозможно повторно инициировать расчёт стоимости без ручного вмешательства.

### 3.4. Контроль и мониторинг
- Отсутствуют централизованные метрики (Prometheus / Grafana).
- Нет алертинга при скоплении сообщений в очереди или деградации производительности.
- DevOps-инженер единственный, CI/CD — частично ручной → увеличивает time-to-market и вероятность ошибок.

### 3.5. Процессы и качество релизов
- E2E-тестирование выполняется вручную, без автоматизации → частые задержки релизов.
- Нет тестового контура для нагрузочного тестирования.
- Разделение окружений (dev, release, prod) логическое, но не изолированное по ресурсам.

### 3.6. Архитектурные риски
- **Сильная связанность систем**: CRM ↔ MES ↔ Shop через RabbitMQ без контракта (schema evolution не контролируется).
- **MES** выполняет сразу три роли: расчёт, оркестрация и UI для операторов → монолитная нагрузка и технический долг.
- Нет буфера между внешними API и внутренним RabbitMQ → перегрузки от партнёров приводят к cascade failure.

### 3.7. Видимость данных и прозрачность для клиентов
- Отсутствие трекинга заказов: клиенты не видят статусы своих заказов в реальном времени
- Отсутствуют уведомления об изменении статусов заказов.
- Клиенты вынуждены обращаться в поддержку для получения базовой информации о своих заказах

## 4. Инициативы по устранению проблем

| №  | Инициатива                                                                                      | Цель | Категория          |
|----|-------------------------------------------------------------------------------------------------|------|--------------------|
| 1  | Ввести асинхронный расчёт стоимости через очередь / job scheduler                         | Разгрузить MES API, улучшить масштабирование | Архитектурная      |
| 2  | Внедрить DLQ, retry и мониторинг очередей RabbitMQ                                         | Повысить надёжность интеграций | Интеграционная     |
| 3  | Разделить MES API на отдельные сервисы (pricing, manufacturing, monitoring)                | Уменьшить связанность, повысить масштабируемость | Архитектурная      |
| 4  | Добавить Redis / PostgreSQL cache для дашборда операторов                                  | Ускорить загрузку и снизить нагрузку на БД | Производительность |
| 5  | Добавить Prometheus + Grafana + алертинг (CPU, очередь, latency)                           | Повысить наблюдаемость и реакцию на инциденты | Инфраструктура     |
| 6  | Ввести throttling и rate limiting для API-партнёров                                       | Защитить MES от перегрузок внешними запросами | Интеграционная     |
| 7  | Внедрить автотесты E2E + smoke на release окружении (Selenium / Cypress)                   | Сократить задержки релизов | Качество           |
| 8  | Ввести CI/CD full automation (GitLab CI / Jenkins)                                         | Ускорить поставку и уменьшить ручные ошибки | Инфраструктура     |
| 9  | Ввести трассировку событий (Elastic APM / OpenTelemetry)                                   | Улучшить анализ инцидентов | Observability      |
| 10 | Постепенный переход к микросервисной архитектуре (сервис расчёта стоимости, сервис заказов) | Подготовка к масштабированию | Стратегическая     |
| 11 | Создать систему трекинга заказов (Order Tracking)                                           | Повысить прозрачность для клиентов и снизить нагрузку на поддержку | Бизнес / UX        |
| 12 | Усиление команды DevOps/QA                                                                 | Дополнительные ресурсы под рост системы. | Стратегическая     |

## 6. Целевая архитектура через 6 месяцев

### Основные характеристики
- MES разделён на три сервиса:
  - `pricing-service` (C#, async worker)
  - `manufacturing-service` (C#, REST API)
  - `monitoring-service` (React dashboard + Redis cache)
- Все сервисы публикуют события в **Kafka / RabbitMQ с DLQ и retry**.
- Введён **обратный API** от CRM для подтверждения заказов.
- Внедрена **система метрик (Prometheus + Grafana)** и **трассировка (OpenTelemetry)**.
- CI/CD полностью автоматизирован.
- Дашборд MES использует кеширование Redis и индексированные запросы.
- API внешних партнёров защищён rate limiter-ом и очередью входящих задач.
- Введён отдельный **Order Tracking Service** с REST/WebSocket API для клиентов.

## 7. Топ-3 инициативы на ближайшие полгода

1. **Асинхронизация расчёта стоимости (pricing jobs)**  
   → снимет до 60–70% текущей нагрузки с MES и устранит основной источник задержек заказов.

2. **Надёжность очередей (DLQ + мониторинг)**  
   → предотвратит потерю заказов и жалобы B2B-партнёров.

3. **Оптимизация дашборда MES (Redis cache, индексирование)**  
   → повысит отзывчивость интерфейса операторов, сократит жалобы и улучшит производительность БД.
